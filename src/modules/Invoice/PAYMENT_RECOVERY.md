# Interrupted saved payments

Open **Transactions → Payment recovery** to see unresolved saved-payment attempts and processing transactions. The queue shows up to 500 oldest records in each category. A pending attempt may be a legitimate bank debit still clearing.

New saved charges commit an immutable attempt ID before contacting the gateway, and record a returned payment reference before local settlement. Stripe and PayPal REST receive this ID as part of their provider idempotency key. Unresolved attempts block staff, client and automatic charges. They are never retried by sending another charge, even after provider idempotency retention expires. Legacy PayPal reference transactions also receive an attempt-specific `MSGSUBID`, limited to 38 bytes; their transaction details can also be read during recovery.

Stop the original worker before reconciliation. **Check gateway** only reads Stripe PaymentIntents, PayPal REST captures, or legacy PayPal transaction details and verifies invoice ownership, gateway metadata where available, and currency. If a reference was lost, staff can supply one from the provider dashboard. A missing reference or unsupported lookup means **unknown**, not failed. Network errors do not release the attempt.

**Reconcile existing attempt** processes the existing payment through the normal settlement path, or records a definitive failure. Existing transaction records are reused. An interrupted transaction must first be released on its transaction page, after checking its worker and gateway outcome. Pending bank debits stay blocked until they settle or fail. Recovery never initiates another charge.

If the provider confirms that no payment exists and there is no recorded reference, staff may explicitly record that outcome with a reconciliation note. The attempt retains the staff ID, note and resolution source in the database. A later charge gets a new attempt ID. Automatic retries remain held after an ambiguous outcome; staff can deliberately charge after resolving it.

Each transaction processing claim stores a new random 128-bit `processing_token`. A worker captures its token at claim time; refreshing an entity never gives that worker a replacement token. Release atomically clears only the token staff reviewed, and the next claim gets a different token. A stale browser form cannot release a newer claim.

A saved charge has two separate identifiers: its immutable attempt ID scopes provider idempotency, while `owner_token` controls local writes. Recovery rotates the ownership token even when the provider still reports pending, keeping the original request ID and payment reference. The original worker then loses write authority without issuing another charge.

The application database middleware checks every active ownership token under a row lock in the same transaction as the SQL. This covers raw DBAL operations, statements prepared before takeover, ORM flushes, invoice and wallet settlement, refund/accounting writes initiated by that worker, API calls and event listeners. An autocommit statement gets a short transaction; existing financial transactions retain the claim lock through commit or rollback. MySQL/MariaDB payment transactions use `READ COMMITTED` for that transaction only: claim and financial row locks provide serialization while allowing duplicate-credit recovery to see a receipt committed after an earlier read. The session isolation setting is preserved. Revocation waits for that transaction: it cannot occur between the ownership check and its writes. Failure recording also compares the captured token, including after Doctrine closes its manager. Nested charge and transaction scopes must both remain valid. An ownership failure invalidates the complete scope, even if an adapter catches the exception. Processing entry points close their entity manager on failure so stale dirty objects cannot escape into a later flush.

All application connections, including isolated entity managers, install the guard. Processing entry points reject an unfenced primary connection; guarded connections allow only ordinary data statements and read-only inspection, plus exact session controls required by DBAL. They reject native PDO access, DDL, multiple SQL statements, implicit-commit controls such as MySQL `LOCK TABLES`, explicit transaction SQL or a transaction leaked past its processing scope. Adapter extensions must use the application DBAL/Doctrine connection and balanced transaction APIs. A connection with an uncertain commit outcome must be replaced. Independent Stripe cache managers share the connection when a financial transaction is already open, avoiding a second session waiting on the first session's fence lock.

Normal built-in updates coordinate participating requests and cron before replacing files, then apply configuration and schema changes through the finalization flow. Users do not need to run SQL or release processing claims as a routine upgrade step. Legacy processing rows and charge attempts have null tokens; explicit recovery hands an interrupted payment to the new protocol. The admin release API requires the `claim_token` from the latest admin transaction response (an empty string for a legacy null claim), as well as reconciliation confirmation.

The first transition from a release without runtime coordination cannot retroactively fence a process already running that older code. The release path uses a coordination-capable intermediate release before Phase B/C; see `tools/upgrade-bridge/README.md` for the publication and old-worker lifetime requirements. Manual file replacement and nodes with independent lock storage need their own coordinated rollout. Stop the old workers before reconciling their payments. Ordinary automatic updates between coordination-capable releases drain application readers themselves; they do not require users to manage PHP worker processes.

Wallet credits carry a unique `payment_key` derived from the gateway's payment reference and credit type. A retry verifies the original client and amount and reuses the committed credit; concurrent callback rows converge on that same key. The insert uses a savepoint so a unique-key race does not close the shared manager. This also covers a worker displaced after crediting the wallet but before completing the invoice. Stripe subscription redirects and invoice webhooks use the same gateway invoice reference.

Existing transactions migrate with a null `credit_recovery_state`. Their first wallet credit is blocked until staff explicitly reconciles the history; the system cannot infer that a historic unmarked credit is absent. A fresh callback also stops when an older transaction or unmarked wallet entry matches its provider reference. On the transaction page, **Reconcile existing wallet history** either links the verified existing positive credit or records an explicit, noted confirmation that no credit exists. Linking validates the invoice client, gateway credit type, amount and verified payment reference. It changes no wallet amount. Both choices atomically revoke the reviewed processing claim and save the staff note. Process the existing payment afterwards. A stale form, another client's credit, a mismatched amount or a previously assigned credit is rejected. When a reference or amount is missing, enter the verified details first. Historical financial discrepancies still require staff review; age alone never authorizes another credit.

The session lock prevents recovery overlapping a live charge worker. Fencing protects local database state if that lock is lost or an old worker resumes. These mechanisms cannot undo a request already sent to a provider. Never declare “no payment” based only on elapsed time or a missing local record. For unknown outcomes, the provider dashboard or provider support remains the authority. Existing transactions created before this journal still require the transaction-page recovery workflow.


Stripe subscription retries retain the original wallet-credit owner and reuse a recorded subscription ID instead of creating another subscription. Once a transaction owns a durable receipt, recovery uses that receipt rather than the subscription's mutable latest invoice. Other callbacks record zero additional payment income, including while the local invoice remains unpaid. Invoice webhooks reuse the renewal invoice linked to that receipt's original transaction. For an already credited receipt, a missing subscription ID or uncertain renewal-invoice link stops processing for staff reconciliation. A paid invoice without a matching receipt also stops. These checks never authorize another charge or renewal invoice. Verify those references with Stripe and correct the existing transaction before retrying it. An original receipt owner is retained even if another callback completed first.
